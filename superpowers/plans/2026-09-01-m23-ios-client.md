# Milestone 23 iOS Client Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement the iOS half of Milestone 23 — the SMS-integration capability toggle, the device-invocation compose-sheet flow, the "Forward message to Veetbot" App Intent, the three device-channel API routes on the client, and the documented owner ceremony — leaving only the owner's physical-iPhone verification.

**Architecture:** Everything extends the existing Apple client (SPM `VeetbotCore` + hand-edited Xcode app target) exactly as `docs/plan/device-channel-and-sms.md` §"The iOS client and the owner ceremony" designs: the capability rides device registration (re-registration via a fresh APNs token request); a `DEVICE_INVOCATION` push tap fetches pending invocations and presents a prefilled `MFMessageComposeViewController` whose dismissal posts the one terminal result; an in-app App Intent (no extension, no app group) posts captured SMS to the ingest route.

**Tech Stack:** Swift 5 (SPM tools 6.0), iOS 15 deployment floor (guard newer API with `@available`), macOS 12 compiles `VeetbotCore` too (`#if os(iOS)` guards), Swift Testing for unit tests, MessageUI, AppIntents (iOS 16+; capture needs iOS 17 Shortcuts).

**Spec:** `docs/plan/device-channel-and-sms.md` (canonical; §"The iOS client and the owner ceremony", §"SMS ingest", §"device.sms.send"). Client seam reference (read before implementing ANY task): `superpowers/reference/m20-apple-client-map.md` — its file:line anchors are cited below as "map §N"; the map predates the milestone renumbering (its "M20" = Milestone 23) and anchors may have drifted — re-grep on miss. // DeviceInvocationService.swift — pure logic over an API protocol, fully testable.
```swift
public protocol DeviceInvocationAPI: Sendable {
    func pendingInvocations(deviceID: UUID) async throws -> DeviceInvocationList
    func postInvocationResult(deviceID: UUID, invocationID: UUID, result: DeviceInvocationResult) async throws -> DeviceInvocationResultView
}
extension VeetbotAPIClient: DeviceInvocationAPI {}

public struct SmsInvocation: Equatable, Sendable {
    public let id: UUID; public let recipient: String; public let body: String; public let expiresAt: Date
}

public struct DeviceInvocationService: Sendable {
    public init(api: DeviceInvocationAPI, deviceID: UUID, now: @Sendable () -> Date = Date.init)
    /// Fetch, keep tool_name == "device.sms.send", drop rows with expires_at <= now
    /// (posting "expired" for each dropped row), parse arguments {recipient, body}.
    public func nextSmsInvocations() async throws -> [SmsInvocation]
    /// Maps MessageComposeResult → sent/cancelled/failed and posts it.
    /// A thrown conflict (409) is swallowed: the row is terminally settled server-side.
    public func complete(_ invocation: SmsInvocation, with result: DeviceInvocationResult) async
}
```

`SmsComposeSheet.swift` (all inside `#if os(iOS)` + `import MessageUI`): a `UIViewControllerRepresentable` wrapping `MFMessageComposeViewController` prefilled with `recipients: [invocation.recipient]`, `body: invocation.body`; its coordinator receives `didFinishWith result:` and calls a `(MessageComposeResult) -> Void` closure (`.sent → .sent`, `.cancelled → .cancelled`, `.failed → .failed`), then dismisses. A guard helper `SmsComposeSheet.canSend` returns `MFMessageComposeViewController.canSendText()`; the presenting flow posts `.failed` when it is false. Presentation: the delegate's `device_invocation` response routes through the existing `NotificationDeepLink`-style plumbing to the SwiftUI layer — add a published `pendingSmsInvocation: SmsInvocation?` on `ChatViewModel` (map §5's `openNotification` stash-and-replay idiom) that `RootView` presents as a `.sheet` (iOS-only conditional). On sheet dismissal call `service.complete`.
