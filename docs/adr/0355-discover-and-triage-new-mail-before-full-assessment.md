# ADR-0355: Discover and triage new mail before full assessment

- Status: Accepted, 2026-11-25
- Approved as ADR-0354 on the email feature branch. Registered as ADR-0355 on dev because ADR-0354 was already assigned there.
- Scope: Milestone 26, both existing Gmail accounts for local discovery and ordering; eligible work mail for Jev.
- Amends [server arrival checks](0286-server-checks-for-new-mail.md), [new-mail processing order](0298-new-mail-slices-assess-only-arrivals.md), and [Inbox visibility](0329-inbox-relevance-floor.md).
- Related: [standing work-account junk filtering](0244-standing-owner-email-junk-filter.md) and [email quality requirements](../plan/email-experience.md).

## The failure

A work message took 10 hours 9 minutes from Gmail arrival to its first full-thread read. During that interval the maintenance worker logged 103 budget refusals. Aggregate rolling spend was about USD 558.30 at the first refusal, above the USD 540 background threshold. A foreground refresh eventually saw the new message in Gmail history. It read seven other threads and reached the message on the following refresh. The model could only make a decision after that read.

The two history pages in that first foreground refresh contained 32 distinct live thread candidates. Five initially had an incoming message labeled Important and Inbox. Replaying later label changes left three qualifying inbound Inbox threads. The reported thread moved from thirteenth to second when those three went first with the same recency tie-breaker. The read-only comparison in `scripts/email_triage_history_replay.sql` uses only labels available in the observed history pages. This replay establishes that the signal was available before retrieval and would have fit in the observed seven reads. It does not establish the time of a hypothetical model completion.

The failure reaches the UI. A fresh thread with no assessment starts at zero. The Inbox relevance floor is 0.1. A delayed assessment can therefore keep incoming mail out of both the ordinary Inbox and Important. Search and Other remain available to an owner who already knows to look.

The ledger records cost by run, which can include several assessments and drafts. Multiplying these counts by average call cost would overstate the precision of a savings estimate.

The long delay also appeared outside the reported thread. This diagnostic excludes unseen mail, replies that revised a thread, and long historical imports. It measures import, not visibility. A Gmail label alone misses useful cases even against this imperfect model-derived reference.

It would have admitted the reported check at the observed spending level. At a hard cap the whole refresh would still be refused, and its read and assessment ordering would still be unchanged.

## Decision

1. **Discover independently of paid work.** A due poll performs bounded Gmail history reads using the existing account-qualified read capability. In one transaction, upsert pending work and checkpoint each admitted history page. A discovered change survives a worker crash, a paid-budget refusal, and a foreground refresh joining a running check. Never advance a source watermark past uncommitted work. Resume from a durable cursor after a burst. A stale cursor triggers a bounded Inbox resync with the same admission rules. Charge Gmail quota and apply provider backoff independently. This path cannot invoke a model, draft, memory formation, historical processing, or a Gmail mutation. A long-running assessment must not hold the discovery lease.

2. **Stage one decides who gets the next read and full assessment.** Preserve authenticated provider signals available at discovery. Distinguish a new inbound message from a label edit or an outgoing reply. Merge label additions and removals in provider order; cancellation, Spam, Trash and deletion supersede earlier signals. Use current owner feedback, prior verified correspondence and the Gmail Important hint to expedite likely important arrivals. Known reply partners and protected correspondence can proceed directly to full assessment. A new correspondent without a Gmail label gets a bounded opportunity for review. Fetch the newest inbound evidence first when a thread history spans many pages; mark partial evidence explicitly. For multi-account or sustained priority bursts, allocate aged ordinary work a share of reads and assessment slots. A merely recent change or repeated label edit cannot keep moving an older candidate to the back.

3. **Use Jev on eligible work mail.** Keep the existing reviewed junk decision, its exact input, model, protections, admission limit and evidence binding. Apply a separately versioned positive decision only when local signals and the standing junk verdict have left an eligible work message undecided. It may nominate that message for immediate full assessment, including unfamiliar senders with material requests or important informational updates. It may use only the already permitted evidence after the egress checks. The offline importance evaluator's richer inputs include private relationship information and cannot be sent by this production path. Cache each decision by source revision, account, owner, protection state, policy and model. Coalesce duplicate attempts, meter each attempt and preserve conservative settlement for unknown outcomes. A timeout or uncertainty sends the message to the age-bounded full-assessment queue. A positive decision can only advance a message. The approved junk verdict alone can skip the full call. Personal mail uses local signals and full assessment; extending Jev to it needs its own reviewed inputs and account authorization.

4. **Stage two establishes importance and reply need.** The existing full assessor owns the grounded score, explanation, urgency and reply decision. A qualifying arrival takes the next available paid slot. Reserve capacity inside both daily and rolling limits for expedited work before routine assessment, drafts, old passages and historical learning. Scope that reservation across all spenders of the same allowance, including foreground work; a refresh share alone cannot reserve it. Coalesce by account, thread and content revision, and fence the save against new mail, changed feedback, archive, erasure and a lost lease. Isolate draft and memory failures from the durable rank. Keep score, timely owner visibility, and draft completion separately observable.

5. **Make a waiting message visible.** Publish a provisional Inbox entry for a likely important arrival as soon as its identity and Inbox state are verified. Explain whether full review is queued, budget-held or delayed by a provider. Its provisional status carries neither a fabricated score nor a reply instruction. When a hard monetary cap prevents processing, the owner can still open the message. The provisional row shows the verified sender and subject, subject to the existing source access and retention rules. A later full assessment reconciles the row once, including its counts, across devices. A subsequent delete, archive, revoked account or owner correction immediately changes eligibility. Do not weaken the calibrated final Important list or generate unsolicited push alerts.

## How this saves money

Keep the 93 observed work bypasses as the baseline. Incremental savings require avoiding additional low-value full assessments or duplicate paid work. Reordering calls and postponing drafts can improve latency while leaving total spend unchanged. Extra Jev calls can increase spend. Record cost by stage and source revision so the paired replay can compare full calls avoided, added decision costs, and any later catch-up on the same cohort. Continue tracking costs after queues drain. A queue of unpaid work at the end of a measurement window is deferred expense.

Keep informative bulk, receipts, security alerts, financial obligations, unfamiliar personal mail and protected sources in the quality sample. Independently review the 38 keep-then-bulk work cases alongside important keeps, protected cases and ordinary low-priority arrivals. Only if this exposes a distinct safe-to-skip population should a new negative decision be proposed. Its labels, evaluation and approval are separate from positive promotion. Existing calibration covers the current work-only junk policy and cannot be transferred to new questions or personal mail.

- Replay the reported queue shape with synthetic identities, seven available reads, a protected participant and newer low-value mail. Exercise missing and removed labels, an important first contact with no history, important FYIs with no reply, deleted and archived mail, old persisted cursors, duplicate history pages, source changes during assessment, and a crash between discovery and assessment.
- Measure provider arrival, first observation, first visible row, first triage decision, full assessment start and first grounded result per source revision. Compare p50, p95 and maximum by account, budget state and disposition. Track undiscovered arrivals against an independent bounded Gmail reconciliation sample. Include still-pending cases as censored delays, and report API outages and hard-cap holds separately.
- Proposed service targets at the current five-minute poll interval: p95 arrival to visible provisional row within 10 minutes for owner-labeled important arrivals, and p95 arrival to first grounded result within 15 minutes while paid capacity is available. A known likely-important item waiting over 15 minutes must have a visible cause. These are acceptance targets to test under bursts and simultaneous account traffic.
- Run paired chronological replays on the same arrivals, budgets and candidate pools. Compare current production, the dev budget change alone, local priority signals alone, and local signals plus Jev. Report full calls on owner-labeled junk, dollars per 100 inbound messages including both models, urgent and ordinary wait, and false expedited decisions. Proposed cost gate: reduce full calls on owner-labeled junk by at least 30% and reduce total measured spend per 100 arrivals, at equal or better important-mail coverage. Report the cost and precision trade-off before fixing a production threshold.
- Preserve the existing owner-labeled quality gates, including top-five precision of 90%, each account at least 85%, and top-ten coverage of at least 90% on eligible snapshots. Review every missed important thread. Require zero owner-labeled important items suppressed by a new shortcut in the reviewed set. Use held-out complete candidate pools and evidence available at arrival, with at least 30 snapshots and 100 held-out priority judgments. An offline candidate that fails to beat local ordering can be left off.
- Deliver in reversible increments: model-free discovery and pending visibility first, then local scheduling, then a work-only Jev shadow comparison. Shadow cannot suppress, reorder or trigger a draft. Enable positive promotion only after measured latency, quality and cost justify it. Rollback stops new decisions, requeues pending work under the previous policy, and preserves Gmail cursors, viewability and already charged attempts. The existing owner-filter kill switch remains independent.

The owner approved the two-stage workflow on 2026-11-25 and selected time from Gmail receipt to first membership in the owner's Important inbox as the figure of merit. Measure p50, p95 and maximum. Track arrivals still waiting alongside completed placements, and compare dollars per 100 observed arrivals under the same caps. A provisional row and a grounded low ranking are separate outcomes.

In the paired synthetic worker replay, the board conversation arrived two minutes before polling, followed by twelve newer promotions. With the same scripted assessor, poll interval and budget, time to Important fell from 17 minutes to 2 minutes and its full-assessment position moved from 13 to 1. Both queues drained after 13 full calls and settled at the same USD 1.30 using a synthetic USD 0.10 per call. In the PostgreSQL replay, discovery occurred at the hard cap, and the first eligible paid poll placed the conversation in Important at seven minutes from receipt. In a replay charging two seconds for each provider thread read, promptly checkpointing the ordinary backlog reduced receipt-to-Important time from 136 to 124 seconds. The worker still served an ordinary read. An unlabeled first contact in the oldest ordinary position also took the first assessment slot. The fixtures use a simulated clock. Production latency, owner-labeled recall and realized savings still require a measured rollout.

## Rules settled in review, 2026-11-25

- **The reserved slice.** When a refresh fits the allowance only by using the slice reserved for expedited arrivals, it is admitted in the expedited scope. In that scope its paid work is the full assessment of expedited arrivals: it assesses no ordinary mail, prepares no draft and resumes no re-rating. Its reservation is therefore the reserved slice in use, and a refresh that arrives while it works joins it or is held to discovery.
- **Whose check failed.** The wait between server checks widens only when a server check fails. The budget can also hold a foreground refresh to discovery or to expedited arrivals, so scope cannot tell the two apart. Each refresh task records whether the server's check asked for it. A task written before that was kept counts as a server check only in the `arrivals` scope.
- **Cached mail.** A historical import can cache a recent inbound Inbox message with no arrival. Its first live observation starts the arrival and records the discovery receipt while that content still awaits assessment, without changing the source revision. Mail that already has an assessment needs no expedited path and gets no arrival.
- **A lost nomination.** When an unassessed arrival stops being expedited, the stored wait that only its nomination explained is cleared.
- **Sender checks.** Gmail's sender check applies to one message. A message that failed it lends no partner evidence to a later message from another sender.
- **Deleted source sessions.** The owner may delete the session a conversation was read in. Marking that conversation Important, or restoring it, still succeeds: the placement is kept on the conversation's arrival record. The timing event is written to the newest source session that still exists and is omitted when none does, since the discovery receipt it would be compared with was deleted with its session.
- **Retry times.** A budget refusal names a retry time only if the same gate, applied with that day's own spending, would admit the work then.
